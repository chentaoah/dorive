### 领域驱动设计

领域驱动设计的核心理念可以概括为：**以业务领域为核心，通过统一语言和模型驱动设计，将复杂的业务逻辑清晰地映射到软件实现中**。其关键要点包括： 

1. **聚焦核心域**
   识别并优先投入资源到业务最核心、最有价值的部分（核心域），而非通用子域或支撑子域。
   
2. **统一语言**
   在业务专家、开发人员等所有角色之间，建立一套基于领域模型的共同语言，避免术语歧义。
   
3. **限界上下文**
   明确定义模型的应用边界，不同上下文内的模型可以独立演进，通过上下文映射进行集成。
   
4. **模型驱动设计**
   设计一个与业务模型紧密对应的软件模型，模型不仅用于分析，更直接指导代码实现。
   
5. **分层架构与实体、值对象、聚合、领域服务、领域事件等战术模式**
   用具体的设计模式来封装复杂的业务规则，保持领域层的纯粹性，避免技术逻辑侵入。
   
6. **持续迭代与协作**
   强调业务与技术团队的深度协作，通过持续重构保持模型与业务发展的同步。

简而言之，DDD 不是单纯的技术架构方法，而是一种**业务复杂性管理策略**，帮助团队在复杂业务场景中创建可演进、可理解的软件。 



### 模块化

结合领域驱动设计（DDD）来谈模块化，核心观点是：**模块化不是技术上的代码拆分，而是对业务领域的逻辑切分**。DDD 中的模块（Module，也称包）应该直接反映领域中的概念边界。

#### 模块的本质：业务概念的容器

在 DDD 中，模块用来容纳**内聚性高、耦合性低**的一组领域对象（如实体、值对象、领域服务、领域事件等）。

- **好模块的标志**：模块名能清晰地表达一个业务概念（如 `Billing`、`Inventory`、`RiskManagement`）。

- **坏模块的标志**：模块名是技术性的（如 `Utils`、`Helpers`、`Models`），或者一个模块里混合了多个不相关的业务概念。



### 模块化范式

####  核心特点 

1. **命名空间隔离**
   模块的包名、配置项、Bean 名称、表名、请求路径等各自独立，互不冲突。
   
2. **独立运行与测试能力**
   每个模块可单独运行、独立测试，不依赖完整应用环境。
   
3. **可控的对外暴露能力**
   模块可主动控制哪些接口或能力对外暴露，隐藏内部实现。
   
4. **基于接口或事件的交互方式**
   模块间通过明确定义的接口或事件机制通信，避免直接耦合。
   
5. **显式的依赖与资源声明**
   模块必须明确声明自己所依赖的其他模块或资源，以及自身提供的资源。
   
6. **支持多版本共存**
   同一模块的不同版本可同时运行在同一系统中。
   
7. **配置与代码一致性**
   模块的配置信息与代码实现保持语义一致，避免配置与逻辑分离带来的不一致问题。

#### 总结

| 维度       | 特征描述                                       |
| :--------- | :--------------------------------------------- |
| **隔离性** | 命名空间（包、配置、Bean、表、路径等）完全独立 |
| **自治性** | 可独立运行、独立测试、独立部署                 |
| **封装性** | 控制暴露接口，隐藏内部实现                     |
| **透明性** | 依赖关系显式声明，可审计可分析                 |
| **兼容性** | 支持多版本共存，实现平滑演进                   |
| **一致性** | 配置与代码统一管理，消除环境差异               |
